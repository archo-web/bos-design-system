# layout-patterns.md — BOS 4.0 레이아웃 패턴

> 이 문서는 BOS 4.0 시스템의 **페이지 레이아웃 표준**을 정의합니다.
> 새 화면을 만들 때, 처음부터 그리지 말고 여기 정의된 12가지 패턴 중 하나를 선택해서 시작하세요.

---

## 🎯 왜 레이아웃 패턴이 필요한가

업무용/마케팅용 화면은 같은 종류의 화면이 반복됩니다 (리스트, 디테일, 폼, 대시보드, 인증, 마법사…).
같은 종류의 화면이 매번 다르게 생기면 사용자는 매번 새로 학습해야 합니다.
**12개 패턴으로 화면의 98%를 커버**하고, 사용자가 어디 가든 익숙한 구조를 보게 합니다.

---

## 📐 글로벌 레이아웃 (모든 페이지 공통)

```
┌─────────────────────────────────────────────────────┐
│  Navbar (height: 64px, fixed top)                   │
├──────┬──────────────────────────────────────────────┤
│      │                                              │
│ Side │  Main Content Area                           │
│ bar  │  padding: spacing-6 spacing-8 (24~32px)      │
│ 288px│  max-width: container-2xl (1440px)           │
│ (접기│                                              │
│ 60px)│                                              │
│      │                                              │
└──────┴──────────────────────────────────────────────┘
```

**구성 요소** (BOS 4.0 컴포넌트)
- **Navbar**: 상단 고정. 높이 `64px`. `bg-primary` 배경, `border-base` 하단 보더.
- **Sidebar**: 좌측. 펼침 `288px`, 접힘 `60px`. `bg-primary` 배경 (BOS 4.0 Figma 기준).
- **Main Content**: 좌우 패딩 `spacing-8` (32px), 최대 폭 `container-2xl` (1440px).

**원칙**
- Navbar와 Sidebar는 **모든 업무용 페이지에서 동일**해야 함
- Main Content 영역에서만 페이지별 패턴이 달라짐
- 마케팅 페이지는 Sidebar 없이 Navbar만 사용 (전체 폭)
- Auth/Onboarding 페이지는 Navbar/Sidebar 모두 없이 중앙 정렬

## 📋 12가지 패턴 한눈에 보기

| # | 패턴 | 용도 한 줄 | 빈도 |
|---|---|---|---|
| 1 | **List Page** | 같은 형태 여러 항목 탐색·관리 | ⭐⭐⭐⭐⭐ |
| 2 | **Master-Detail** | 좌측 리스트 + 우측 상세를 한 화면에 | ⭐⭐⭐⭐ |
| 3 | **Card Grid** | 시각적 항목(상품·이미지·프로젝트)을 카드로 | ⭐⭐⭐⭐ |
| 4 | **Detail Page** | 한 항목을 깊이 있게 보기 | ⭐⭐⭐⭐⭐ |
| 5 | **Modal Form** | 5필드 이하의 짧은 입력 | ⭐⭐⭐⭐⭐ |
| 6 | **Page Form** | 6필드 이상 또는 섹션 분리가 필요한 입력 | ⭐⭐⭐⭐ |
| 7 | **Wizard / Stepper** | 여러 단계로 나눠 입력해야 하는 긴 프로세스 | ⭐⭐⭐ |
| 8 | **Dashboard** | 여러 KPI/차트를 한눈에 비교 | ⭐⭐⭐⭐ |
| 9 | **Settings** | 카테고리별 환경설정 | ⭐⭐⭐⭐ |
| 10 | **Auth Page** | 로그인/회원가입/비밀번호 재설정 | ⭐⭐⭐ |
| 11 | **Onboarding** | 첫 진입 사용자에게 핵심 기능 안내 | ⭐⭐ |
| 12 | **Empty / 404 / Error** | 데이터 없음·페이지 없음·오류 안내 | ⭐⭐⭐ |

## 🚦 패턴 선택 의사결정 트리 (다면적)

이 트리는 **3가지 관점**으로 같은 결정을 검증합니다. 한 관점만 보고 결정하지 말고, 적어도 두 관점이 같은 패턴을 가리키는지 확인하세요.

### Step 1 — 액션 동사 (사용자가 "무엇을 하려는가")

```
사용자가 이 화면에서 하려는 동사는?
├─ 본다 / 찾는다 (조회·탐색)
│   ├─ 동일 형태 여러 개 → 1·2·3
│   ├─ 한 항목 깊이      → 4
│   └─ 여러 지표 동시    → 8 (Dashboard)
│
├─ 한다 / 보낸다 (입력·실행)
│   ├─ 짧은 폼 (≤5필드)  → 5 (Modal Form)
│   ├─ 긴 폼 (≥6필드)    → 6 (Page Form)
│   └─ 단계적 흐름       → 7 (Wizard)
│
├─ 바꾼다 (설정 변경)    → 9 (Settings)
│
├─ 진입한다 (인증·온보딩)
│   ├─ 로그인/가입       → 10 (Auth)
│   └─ 첫 사용 안내      → 11 (Onboarding)
│
└─ 오류·없음을 만났다    → 12 (Empty/404/Error)
```

### Step 2 — 정보 구조 (데이터/콘텐츠 모양)

```
이 화면에 담을 콘텐츠의 모양은?
├─ 같은 스키마 행 여러 개 (테이블형 데이터)
│   ├─ 빠른 스캔 + 행 클릭 → 1 (List Page)
│   └─ 행 클릭 시 우측에 상세 → 2 (Master-Detail)
│
├─ 같은 스키마 카드 여러 개 (시각적 항목)
│                            → 3 (Card Grid)
│
├─ 단일 항목, 다층 정보 (속성 + 관련 데이터 + 활동 로그)
│                            → 4 (Detail Page)
│
├─ 단일 폼 (입력 필드 모음)
│   ├─ 짧음 (≤5필드)        → 5 (Modal Form)
│   ├─ 김 (≥6필드)          → 6 (Page Form)
│   └─ 단계 분리 가능 / 필요 → 7 (Wizard)
│
├─ 여러 차원 동시 비교 (KPI · 차트 · 추세)
│                            → 8 (Dashboard)
│
├─ 카테고리별 옵션 묶음
│                            → 9 (Settings)
│
├─ 단일 카드/컨테이너 중앙 정렬
│   ├─ 인증              → 10 (Auth)
│   ├─ 환영/안내         → 11 (Onboarding)
│   └─ 빈 상태/오류      → 12 (Empty/404/Error)
```

### Step 3 — 마이크로 분기 (규모·빈도·맥락)

같은 1단계, 2단계 결과라도 **세부 조건에 따라 패턴을 미세 조정**합니다.

| 조건 | 영향 |
|---|---|
| 항목 5개 이하 | 정렬/페이지네이션 불필요 → 단순 List |
| 항목 10개 이상 | 검색/필터 필수 → List Page (정식) |
| 항목 100개 이상 | 가상 스크롤 또는 서버 페이지네이션 필수 |
| 필드 5개 이하 | Modal Form 사용 가능 |
| 필드 6~15개 | Page Form (단일 섹션) |
| 필드 15개 이상 또는 단계가 명확 | Wizard로 분리 |
| 첫 진입 사용자 | Onboarding 우선 → 이후 정상 패턴 |
| 반복 사용 (매일) | 단축키/빠른 액션 노출 |
| 모바일에서도 사용 | Master-Detail → 단일 화면 전환식으로 |
| 상태가 비어 있을 수 있음 | Empty 상태 디자인 필수 (패턴 12) |
| 실패 가능한 액션 | 에러 상태 디자인 필수 (패턴 12) |

### 검증 — 세 관점이 같은 패턴을 가리키나요?

세 관점에서 모두 **다른 패턴**을 가리킨다면 요구사항이 모호하다는 신호입니다.
사용자에게 한 번 더 질문하세요 — "주된 목적이 X인가요, Y인가요?"

## 🗂 패턴 1: List Page — 리스트형 페이지

가장 많이 쓰는 패턴. 항목들의 목록을 보여주고, 검색/필터/정렬/추가가 가능한 화면.

**용도**: 멤버 목록, 프로젝트 목록, 파일 목록, 주문 목록 등

```
┌───────────────────────────────────────────────────────┐
│  [Title]                            [Primary Action]  │  ← Header
│  설명 텍스트 (선택, text-body)                         │
├───────────────────────────────────────────────────────┤
│  [Search] [Filter] [Filter]    [View Toggle] [Sort]   │  ← Toolbar
├───────────────────────────────────────────────────────┤
│                                                       │
│   Table or Card Grid                                  │  ← Content
│   (스크롤 가능)                                       │
│                                                       │
├───────────────────────────────────────────────────────┤
│                              [Pagination] [10/page ▾] │  ← Footer
└───────────────────────────────────────────────────────┘
```

### 구조 상세

**Header 영역**
- 타이틀: `text-3xl font-bold`, 색상 `text-heading`
- 서브 설명 (선택): `text-sm font-normal`, 색상 `text-body`
- Primary Action: 우측 상단, `Button color="Brand" size="base"`
- 헤더 하단 마진: `spacing-6` (24px)

**Toolbar 영역**
- 좌측: Input field (`Type: Add-on icon` 검색), Dropdown menu (필터)
- 우측: Button group (뷰 전환), Dropdown menu (정렬)
- 좌우 그룹 사이는 `flex justify-between`
- 컨테이너: `bg-primary` + `border-base` + `rounded-base`
- 툴바 하단 마진: `spacing-4` (16px)

**Content 영역**
- 테이블 뷰: BOS 4.0 `Tables` 컴포넌트
- 카드 뷰: BOS 4.0 `Card` 컴포넌트 (Type: Default 또는 With Image), gap `spacing-4`

**Footer 영역**
- 페이지네이션: BOS 4.0 `Pagination` 컴포넌트, 우측 정렬
- per-page 선택: Dropdown menu

### 빈/로딩/에러 상태
```
empty:    Card empty state + Brand CTA
loading:  Skeleton 컴포넌트로 행 모양 유지
error:    Alert (Color: Danger) + 재시도 버튼
```

### 언제 List Page 대신 다른 패턴을 쓸까
- 한 항목이 매우 시각적이고 카드가 더 자연스러움 → **Card Grid (3)**
- 항목 클릭 시 상세 정보 자주 봄 → **Master-Detail (2)**

## 🔀 패턴 2: Master-Detail — 마스터-디테일

좌측에 리스트, 우측에 선택된 항목의 상세를 한 화면에 띄우는 패턴.
**리스트 ↔ 디테일 왕복이 잦은 작업**에 적합합니다 (이메일 클라이언트, 채팅, 멤버 관리).

**용도**: 메시지/알림 관리, 계약서 검토, 멤버 권한 편집, 코드 리뷰

```
┌───────────────────────────────────────────────────────┐
│  [Title]                            [Primary Action]  │
├───────────────┬───────────────────────────────────────┤
│  [Search]     │  [Breadcrumb] / Title                 │
├───────────────┤                                       │
│ ▸ 항목 1      │  선택된 항목의 상세                   │
│ ▶ 항목 2 (선)│                                       │
│ ▸ 항목 3      │  메타 정보, 본문, 액션                │
│ ▸ 항목 4      │                                       │
│   ...         │                                       │
│ [Pagination]  │                                       │
│  list 360px   │       detail (1fr)                    │
└───────────────┴───────────────────────────────────────┘
```

### 구조 상세
- **List 영역 (좌)**: 폭 `360px` 고정. 검색 + 리스트 + 하단 페이지네이션. 선택된 항목은 `bg-brand-softer` 배경.
- **Detail 영역 (우)**: 남은 폭 차지 (1fr). 상단에 Breadcrumb로 깊이 표시.
- 모바일/태블릿에서는 **단일 화면 전환식** — 리스트 → 상세 클릭 → 상세만 표시 → 뒤로가기로 리스트 복귀.

### 컴포넌트
- 좌측 리스트: `Dropdown list item` (48 variants 중 적절한 것) + `Pagination` 또는 무한 스크롤
- 우측 상세: Detail Page 패턴(4)의 컨텐츠를 그대로 가져다 사용 가능

### 언제 List Page 대신 Master-Detail을 쓸까
- 한 화면에서 여러 항목을 빠르게 비교/처리해야 함 (예: 이메일 처리)
- 상세 페이지 진입과 뒤로가기가 비효율적인 경우
- 데스크톱이 주 사용 환경 (모바일이 주이면 List Page가 적합)

## 🃏 패턴 3: Card Grid — 카드 그리드

같은 스키마의 항목을 카드로 펼쳐서 시각적으로 보여주는 패턴.
**텍스트보다 이미지/시각 요소가 핵심**일 때 사용합니다.

**용도**: 상품 카탈로그, 프로젝트 갤러리, 템플릿 선택, 팀원 카드, 부동산 매물

```
┌───────────────────────────────────────────────────────┐
│  [Title]                            [Primary Action]  │
│  [Search]              [Filter] [Sort]                │
├───────────────────────────────────────────────────────┤
│  ┌─────┐  ┌─────┐  ┌─────┐  ┌─────┐                  │
│  │ Card│  │ Card│  │ Card│  │ Card│                  │
│  └─────┘  └─────┘  └─────┘  └─────┘                  │
│  ┌─────┐  ┌─────┐  ┌─────┐  ┌─────┐                  │
│  │ Card│  │ Card│  │ Card│  │ Card│                  │
│  └─────┘  └─────┘  └─────┘  └─────┘                  │
├───────────────────────────────────────────────────────┤
│                              [Load more] or [Pages]   │
└───────────────────────────────────────────────────────┘
```

### 구조 상세
- 그리드: CSS Grid `repeat(auto-fill, minmax(280px, 1fr))`, gap `spacing-4`
- 카드 컴포넌트: `Card` Type 중 `With Image` / `E-commerce` / `Pricing card` / `Grid card` / `User profile`에서 선택
- 무한 스크롤(Load more) 또는 페이지네이션 — 모바일에서는 Load more 권장

### 카드 Type 선택 가이드
| 데이터 성격 | 권장 Card Type |
|---|---|
| 상품/이커머스 | `E-commerce` |
| 프로젝트/문서 | `With Image` 또는 `Default` |
| 사람 (팀원/연락처) | `User profile` |
| 요금제/플랜 | `Pricing card` |
| 후기/리뷰 | `Testimonial card` |

### 언제 List Page 대신 Card Grid를 쓸까
- 항목이 시각적으로 구분되어야 함 (이미지가 결정적인 정보)
- 표 형태로는 정보 밀도가 낮음
- 사용자가 빠르게 훑으며 시각적으로 선택

## 📄 패턴 4: Detail Page — 디테일/상세 페이지

하나의 항목을 깊이 보여주는 화면. 정보 + 관련 액션 + 하위 데이터.

**용도**: 멤버 프로필, 주문 상세, 문서 보기, 이슈 상세

```
┌───────────────────────────────────────────────────────┐
│  [Breadcrumb] List > Item Name                        │
│  [Title]                  [Edit] [Delete] [More ⋯]    │
│  [Status Badge] [Tag] [Tag]                           │
├───────────────────────────────────────────────────────┤
│  [Tab1] [Tab2] [Tab3]  (선택)                         │
├───────────────────────────────────────────────────────┤
│                                                       │
│   Main Information         │  Sidebar (선택)          │
│                            │                          │
│   - 본문                   │  - 메타 정보             │
│   - 첨부                   │  - 관련 항목             │
│   - 활동 로그              │  - 빠른 액션             │
│                            │                          │
│      main (1fr)            │   sidebar (320px)        │
└────────────────────────────┴──────────────────────────┘
```

### 구조 상세

**Header 영역**
- Breadcrumbs: `text-sm`, 색상 `text-body-subtle`
- 타이틀: `text-2xl font-bold` (List Page보다 한 단계 작음 — 컨텍스트가 이미 있음)
- 액션 버튼들: 우측 상단, 우선순위 순으로 (Edit > Delete > More)
- Status Badge: 타이틀 아래 또는 옆 (`Badge` 컴포넌트)

**Tabs (선택)**
- 정보가 많아 분리 필요할 때만 사용 — 적으면 단일 페이지로
- BOS 4.0 `Nav Tabs` 컴포넌트 (`Type: Border bottom` 권장)

**Content 영역**
- 단일 컬럼 또는 좌(main) + 우(sidebar) 2컬럼
- Sidebar는 `320px` 고정 폭, 메타 정보/관련 액션
- Card 컴포넌트로 정보 그룹핑

### 컴포넌트
- `Breadcrumbs`, `Nav Tabs`, `Card`, `Badge` (상태), `Button` (Edit/Delete/More), `Avatar`

### 언제 다른 패턴을 쓸까
- 항목 여러 개를 빠르게 왕복 → **Master-Detail (2)**
- 항목이 매우 단순 → 별도 페이지 없이 **Modal**로 처리

## ✏️ 패턴 5: Modal Form — 모달 폼

5개 필드 이하의 짧은 입력. 현재 페이지에서 컨텍스트를 잃지 않고 빠르게 입력.

**용도**: 항목 추가/편집, 설정 빠른 변경, 초대 보내기, 카테고리 추가

```
       ┌─────────────────────────────────┐
       │  [Title]                    [X] │
       │  설명 (선택)                    │
       ├─────────────────────────────────┤
       │                                 │
       │  Label                          │
       │  [Input field]                  │
       │  helper text                    │
       │                                 │
       │  Label                          │
       │  [Input field]                  │
       │                                 │
       ├─────────────────────────────────┤
       │              [Cancel]  [Save]   │
       └─────────────────────────────────┘
       (max-width: 480px, centered)
```

### 구조 상세
- 모달 컴포넌트: `Modal Type: Create product` 또는 적절한 Modal Type
- Modal header: `Heading & supporting text` 또는 `Default`
- Modal body: 입력 필드 5개 이하 (그 이상이면 Page Form)
- Modal footer: `Modal footer Type: Buttons` (Cancel + Save)
- 폭: `max-width: 480px` (BOS Free component 기준 480~640px)

### 필수 규칙
- Esc 키로 닫기 가능
- 백드롭 클릭 시 닫기 (단, 작성 중이면 확인 다이얼로그)
- Primary CTA 우측, Cancel 좌측
- 작성 중 unsaved changes 안내

### 언제 Page Form으로 전환
- 필드 6개 이상 → **Page Form (6)**
- 단계가 명확하게 분리됨 → **Wizard (7)**
- 입력 중 다른 정보 참고가 필요 → **Page Form (6)**

## 📝 패턴 6: Page Form — 페이지 폼

6개 이상 필드 또는 섹션 분리가 필요한 입력. 단일 화면 안에서 모두 완료.

**용도**: 새 프로젝트 생성, 회원 정보 수정, 결제 정보 입력, 상품 등록

```
┌───────────────────────────────────────────────────────┐
│  [Breadcrumb] List > New Item                         │
│  [Title]                                              │
├───────────────────────────────────────────────────────┤
│                                                       │
│   ─── Section 1: 기본 정보 ───                        │
│   Label                                               │
│   [Input field]                                       │
│   helper                                              │
│                                                       │
│   Label                                               │
│   [Input field]                                       │
│                                                       │
│   ─── Section 2: 추가 정보 ───                        │
│   ...                                                 │
│                                                       │
├───────────────────────────────────────────────────────┤
│                            [Cancel]  [Save draft]     │
│                                          [Save]       │
└───────────────────────────────────────────────────────┘
```

### 구조 상세
- 폭: `max-width: 720px` (단일 컬럼 폼). 좌측 정렬 또는 중앙 정렬.
- 섹션 분리: 헤더는 `text-lg font-semibold`, 섹션 간 간격 `spacing-8`
- 라벨 위치: `Stacked` (라벨 위, 필드 아래) — 가장 빠르게 스캔 가능
- 필수 표시: 라벨 옆 빨간 별표 (`*`)

### 컴포넌트
- `Forms` (Input/Select/Search/Number/Phone form 등)
- `Label` (Default 또는 Required & icon)
- `Helper` (Default 또는 features)
- `Textarea input`, `File upload input`

### 폼 공통 규칙
- 필수 필드는 빨간 별표(`*`)와 `aria-required`
- 에러는 필드 바로 아래 빨간 텍스트로 (필드 위치 앞에 placeholder 형태로 띄우지 말 것)
- "저장" 버튼은 우측 하단, "취소"는 좌측 (또는 그 옆)
- 작성 중 페이지 이탈 시 확인 다이얼로그
- 자동 저장이 가능하면 `Save draft` 버튼 추가

### 언제 Wizard로 전환
- 섹션이 4개 이상이고 각각 독립적
- 사용자가 한 번에 다 채울 수 없는 정보 (단계별 정보 필요)
- 첫 사용자 vs 반복 사용자 흐름이 다른 경우

## 🪜 패턴 7: Wizard / Stepper — 마법사 / 단계별 폼

긴 폼을 여러 단계로 나눠 진행하는 패턴. 각 단계는 명확히 구분되고, 진행 상황을 알 수 있어야 합니다.

**용도**: 회원가입, 결제, 상품 등록(고급), 워크스페이스 만들기, 마이그레이션

```
┌───────────────────────────────────────────────────────┐
│  [Title]                                              │
│  ●━━━○──○──○   Step 2 of 4: 정보 입력                │  ← Stepper
├───────────────────────────────────────────────────────┤
│                                                       │
│   현재 단계의 폼 콘텐츠                              │
│   (단계당 최대 5~7 필드 권장)                        │
│                                                       │
│   helper / 안내 메시지                                │
│                                                       │
├───────────────────────────────────────────────────────┤
│  [Back]                  [Save & Exit]    [Next]      │
└───────────────────────────────────────────────────────┘
```

### 구조 상세
- **Stepper**: 상단에 현재 단계와 전체 단계 표시. BOS 4.0 `Stepper nav link` (35 variants 중 선택). 단계 4개 초과 시 숫자 + 진행 바로 대체.
- **단계 본문**: 단계당 1개의 명확한 목표 (예: "기본 정보", "결제 수단", "검토").
- **하단 네비게이션**: `Back` (좌측, 첫 단계에선 비활성), `Save & Exit` (중앙, 선택), `Next` 또는 `완료` (우측 Primary).

### 단계 설계 원칙
- **단계 수**: 3~5개가 이상적. 6단계 이상이면 사용자 이탈률 급증.
- **각 단계 단일 책임**: "기본 정보 + 결제"처럼 두 가지 섞지 말 것.
- **마지막 단계는 검토(Review)**: 입력 내용 요약 + "수정" 링크.
- **취소/저장 가능**: 사용자가 중단해도 입력 내용 보존 (Save draft).

### 진행 표시
- 단계 ≤ 4개: `Stepper` (점 + 라벨)
- 단계 5~7개: `Stepper compact` (숫자만) 또는 진행 바
- 단계 8개 이상: 패턴 자체를 재검토 (너무 김)

### 언제 Page Form으로 전환
- 단계가 사실상 의미 없을 때 (단순히 길어서 나눈 것)
- 사용자가 정보를 비순차적으로 채우길 원함
- 모바일이 주 사용 환경 (단계 전환 비용이 큼)

- 4개가 적정선, 6개가 한계 (그 이상은 인지 부담)

## ⚙️ 패턴 9: Settings — 설정

카테고리별로 묶인 옵션 변경 화면. **즉시 반영 vs 저장 후 반영**을 명확히 구분.

**용도**: 사용자 환경설정, 알림 설정, 권한 관리, 통합(Integrations), 청구/결제

```
┌───────────────────────────────────────────────────────┐
│  Settings                                             │
├──────────────┬────────────────────────────────────────┤
│              │                                        │
│  General     │  ─── Profile ───                       │
│ ▶ Profile    │  Avatar                                │
│  Notifications│  Name [Input]                         │
│  Security    │  Email [Input]                         │
│  Billing     │                                        │
│  Team        │  ─── Display ───                       │
│  Integrations│  Theme   [Light ▾]                     │
│  Advanced    │  Language [한국어 ▾]                   │
│              │                                        │
│  side 240px  │       main (1fr)                       │
└──────────────┴────────────────────────────────────────┘
```

### 구조 상세
- **좌측 카테고리 네비**: `Vertical with list item` 형태의 Nav Tabs 또는 자체 Sidebar (240px)
- **우측 패널**: 카테고리당 섹션으로 묶기, 섹션 헤더는 `text-lg font-semibold`
- 카테고리 ≤ 3개면 좌측 네비 없이 단일 페이지에 섹션으로 나열

### 즉시 반영 vs 저장 후 반영 — 가장 중요한 결정
- **Toggle 스위치**: 즉시 반영 (예: 알림 ON/OFF) — `Toggle` 사용
- **Form 필드**: 저장 버튼 후 반영 (예: 이름 변경) — `Save` 버튼 명시
- **둘이 한 화면에 있을 때**: 토글은 즉시 반영, 폼은 저장 — UI에서 두 영역을 명확히 분리
- 헷갈릴 만한 곳에는 안내 텍스트 추가 ("자동 저장됨" / "저장 버튼을 눌러야 적용")

### 위험한 액션
- 계정 삭제, 데이터 삭제 등은 별도 영역으로 분리 (`bg-danger-soft` 영역)
- 2단계 확인: 클릭 → "정말로?" 모달 → 텍스트 입력 확인

```
│                  └───────────────────────────────────────┘  │

│                  [홈으로 이동]  [이전 페이지]               │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 4가지 변형 비교

| 변형 | 핵심 메시지 | 발생 원인 안내 | CTA |
|---|---|---|---|
| **Empty** | "아직 항목이 없습니다" | (생략 가능) | 첫 [항목] 만들기 |
| **404** | "페이지를 찾을 수 없습니다" | URL 오타 / 삭제 / 권한 없음 | 홈으로 이동, 이전 페이지 |
| **403** | "접근 권한이 없습니다" | 권한 부족 / 만료된 세션 (보안상 자세히 ✗) | 권한 요청, 로그인, 홈으로 |
| **500** | "잠시 문제가 발생했습니다" | 일시 장애 / 재시도 권장 + 에러 ID | 다시 시도, 새로고침, 고객지원 |

### "발생 가능한 원인" 카드 — Figma 디자인의 차별점

BOS 4.0의 404 디자인은 **단순 사과형 메시지** 대신 사용자가 다음 행동을 추정할 수 있는 **구체적 힌트 카드**를 제공합니다. 이 패턴은 404/500 에러에 특히 효과적입니다.

**원인 카드 작성 원칙**:
- 항목 3개 (그 이상은 인지 부담)
- 사용자 관점에서 작성 ("URL 주소가 잘못 입력되었습니다" ✓ / "404 Not Found returned" ✗)
- 자가 진단 가능한 항목 ("URL 다시 확인" → 사용자가 즉시 확인 가능)
- 보안상 민감한 정보는 제외 (403에선 권한 부족 정도만)

### 공통 원칙
- **차분한 톤**: 사용자 잘못이 아니라는 뉘앙스
- **다음 행동 명확화**: 막다른 길 ✗ → 항상 한 발 앞으로 나아갈 수 있게 ✓
- **유머는 신중히**: 404 페이지의 농담은 평상시엔 좋지만 결제 실패 시엔 부적절
- **CTA 2개**: Primary (홈으로 이동/다시 시도) + Secondary (이전 페이지/고객지원)
- **에러 코드 노출**: Badge 형태로 헤딩 위에 (`ERROR 404`) — 지원 요청 시 식별 가능

### Empty 상태가 적용되어야 할 곳 (체크리스트)
- 모든 List Page, Card Grid → 빈 데이터 시 무엇을 보여줄지
- Master-Detail → 디테일이 선택되지 않았을 때
- Search → 결과 없음
- 알림/Activity feed → 알림 없음
- Inbox → 메일 없음

### 컴포넌트 매핑
- **Card** (원인 안내 박스) — `Card Type: Default`
- **Button** Primary + Secondary — `Button color="Brand"` + `color="Secondary"`
- **Icon shape** (404 큰 비주얼) — 또는 텍스트 "404" 자체를 큰 폰트로
- **Badge** (ERROR 코드) — `Badge color="Danger"` 작은 사이즈

## ❌ 흔한 실수

1. **List Page에서 검색을 빼먹기** — 항목 10개 이상이면 검색은 필수
2. **Form에서 라벨을 placeholder로 대체** — 입력 시작하면 라벨 사라짐, 절대 금지
3. **Detail Page의 Sidebar를 Main과 같은 폭** — Sidebar는 보조 정보, `320px` 고정
4. **Dashboard에 KPI 8개 이상 나열** — 4개가 적정선, 6개가 한계
5. **Modal에서 필드 10개 이상** — Page Form 또는 Wizard로 전환
6. **Wizard 단계 6개 이상** — 사용자 이탈률 급증, 단계 통합 또는 Page Form으로
7. **Master-Detail을 모바일에 그대로** — 단일 화면 전환식으로 변경 필수
8. **Empty 상태 누락** — 빈 데이터 화면이 비어 있는 흰 화면으로 끝나면 안 됨
9. **Settings에서 즉시 반영/저장 후 반영 혼재** — 둘 다 같은 화면이면 시각적 분리 + 명시적 안내
10. **Card Grid를 정보 밀도 낮은 데이터에 사용** — 표가 더 효율적인데 카드로 만들면 스크롤만 길어짐
11. **Auth 페이지에서 자세한 실패 이유 노출** — 보안 위험 (`이메일이 없습니다` ✗)
12. **다크 모드 무시** — 시멘틱 토큰 사용했는지 점검
